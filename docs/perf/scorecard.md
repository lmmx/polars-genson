# The performance scorecard

`scripts/scorecard.py` measures where genson-core spends its instructions, time and memory,
stage by stage, and how one revision changes that against another. On a pull request
labelled `perf-scorecard` a workflow runs it against the PR's base and posts the report as
one comment, updated on each push.

It measures the engine (genson-core), not a downstream pipeline: fixed workloads, generated
from fixed seeds, that stand for the shapes of JSON genson meets.

## What it measures

For each revision and each corpus:

| | how | why |
|---|---|---|
| instructions, by stage | callgrind, one thread, the release build | repeatable to the instruction, so a change of 1% is real |
| instructions per byte | the above over the corpus's size | comparable across corpora and as they grow |
| wall and CPU time | the release build, all threads, interleaved ABBA | what users wait for |
| allocations, bytes, peak live heap, by stage | a debug build with `alloc-stats`, one thread | what the allocator does (the counts do not depend on optimisation) |
| peak RSS | the timing runs | memory as the system sees it (the input included) |
| the output | a hash of the schema (or of the normalised rows), and the processed count | a speed-up that changes the output is not a speed-up |

Each corpus is reported on its own. There is no aggregate score: a gain on one corpus that
costs another shows as such.

## Stages

Each stage runs in a function of its own in `genson-core/src/phase.rs`, never inlined, so
callgrind attributes the stage's instructions by name whatever is inlined within it. The
stages run in turn and none holds another, so their costs add up; what none holds (the
config's clone, freeing the input's results, rayon's own work) is reported as
`unattributed`, and the total is the run's.

| stage | what runs in it |
|---|---|
| `rows` | reading the rows: their interned states (`RowStates::row`), or on the usual paths each row's builder merged into its chunk's and the chunks' into one |
| `merge` | the interned states merged into the builder (`add_interned_row_chunks`) |
| `write_schema` | the builder's schema written out: as a DAG (`to_dag`), or as `Value`s when debugging |
| `rewrite` | fields forced to be maps, then map inference and unification (`rewrite_objects`) |
| `materialise` | the rewritten DAG as a `Value` |
| `reorder` | union types put in order (`reorder_unions`) |
| `avro` | the conversion to Avro (avrotize) |
| `normalise` | normalising rows to a schema (`normalise_values`), in the `normalise` workload |

A stage is one call, so the markers cost nothing measurable when the scorecard is not
running; the allocation counting exists only with the `alloc-stats` feature.

A revision from before the markers is attributed by the functions the stages run, the
largest inclusive cost of each (`LEGACY` in the script). Inlining can hide some of them, so
the report says when it has done this, and its stages are approximate.

## Corpora

Generated by `genson-core/examples/scorecard.rs` from fixed seeds, so no data is committed
and every revision sees the same bytes. The workload uses only
`infer_json_schema_from_strings` and its config (and `normalise_values`), so that revisions
from before the scorecard can be measured with it: the script copies the checkout's
workload into each revision's worktree.

| corpus | rows | what it exercises |
|---|---|---|
| `claims` | 2,000 Wikidata-like claims objects, 15 MB (each property's values of one datatype, as in Wikidata) | wikidata-pq's config: the interned path, map inference and unification of many properties, forced records and promoted scalars, Avro |
| `events` | 20,000 event logs of several kinds | records that differ by kind, the defaults |
| `narrow` | 100,000 small records | the row phase on many short rows |
| `labels` | 1,000 maps of languages' labels | a map of records |
| `entities` | 150 wide Wikidata-like entities | wide, varied records (Avro off: converting their schema is avrotize's cost) |
| `usual` | the event logs, `payload` forced to be a map | a field forced to be a map: once the usual path (per-row builders), now the interned path forcing each distinct row (the name kept, to compare with earlier scorecards) |
| `normalise` | the claims, normalised to their inferred schema | normalisation (inference is done before the runs) |

## Times

Short runs on a shared machine are noisy, and the second of two runs back to back tends to
be faster. So each process times a warm-up run and a measured one, the revisions take turns
in the order base, head, head, base and so on, and the report gives the median with a
verdict: *faster* or *slower* only when the change is at least 3% and the two revisions'
interquartile ranges do not overlap, and the instructions moved too (by more than 0.5%),
otherwise *inconclusive*: a time that moves with no change in instructions is noise.

Stage changes are listed only when both revisions have the stage markers. A revision
attributed by function name puts what inlining hides under `unattributed`, so its stages
are shown but not compared; the totals are exact either way.

## Running it

```sh
# Two revisions: builds each in .scorecard/, measures both, writes scorecard-out/report.md
python3 scripts/scorecard.py compare --base perf/dag-build --head perf/sibling-groups

# And the head against a third revision too (say, the stack's root)
python3 scripts/scorecard.py compare --base HEAD~1 --head HEAD --cumulative master

# A report from two measurements already made
python3 scripts/scorecard.py report scorecard-out/scorecard-<base>.json scorecard-out/scorecard-<head>.json
```

It needs git, cargo, valgrind (with `callgrind_annotate`) and Python 3, and takes about
half an hour for two revisions: two release builds and two debug builds, seven callgrind
runs each, and the timing rounds (`--rounds`, default 6).

## On pull requests

`.github/workflows/scorecard.yml` runs when a PR is labelled `perf-scorecard`, and then again
on each push to it, on reopening, and when its base is changed; or by hand
(`workflow_dispatch`, with any two revisions). It is not a required check.

- **One comment.** The bot keeps one comment per PR, found by its hidden marker
  (`<!-- genson-core-scorecard -->`), and edits it on each run. It names the base and head
  compared, when, and the run.
- **Never stale.** A newer run cancels an older one. Before editing, the comment job reads the
  PR's head and base again: if the head has moved, it leaves the comment to the newer run;
  if the base has moved (a stacked PR's base branch was pushed to), it publishes with a note
  that the base has moved, and the next push or a new label measures against it. A failed
  run replaces the results with a notice and the run's link, the previous results kept
  below it marked stale.

- **The base** is the PR's base commit. A PR stacked on another is compared with the PR
  below it, so each change is credited to the PR that made it. The label
  `perf-scorecard-cumulative` adds a comparison of the head with `master`.
- **Two jobs.** `measure` runs the PR's code with a read-only token and uploads the JSON and
  the report as an artifact (kept 90 days), and writes the report to the job summary.
  `comment` runs none of the PR's code: it downloads the report and posts or updates the
  bot's one comment.
- **Forks.** A fork's PR gets a read-only token, so it gets the artifact and the summary
  but no comment. Commenting on those needs a `workflow_run` workflow on the default branch,
  which reads the artifact of a finished run; it can be added once this is on `master`.

## The JSON

`scorecard-<sha>.json`, one per revision:

```json
{"rev": "perf/sibling-groups", "sha": "4eae9d0...",
 "corpora": {"claims": {
   "rows": 2000, "bytes": 15078434, "processed": 1985, "schema_hash": "…", "attribution": "markers",
   "instructions": {"total": 812000000, "stages": {"rows": 520000000, "merge": …}, "unattributed": …},
   "timing": {"wall": […], "cpu": […], "peak_rss_kb": […]},
   "allocations": [{"stage": "rows", "allocations": …, "bytes": …, "peak_live": …}, …]}}}
```

The artifacts are the history: plotting a series of them shows the engine's costs over
time, stage by stage.

## Not yet covered

- Parquet reading and writing, and normalising straight into Arrow (both behind the
  `parquet` feature), and `extract`: workloads and stages for them are the next to add.
- Wall time by stage: the stages' times could be recorded as their allocations are.
- A history kept between runs (say, on a branch of its own) rather than in artifacts.

## Changing it

- **A stage:** add it to `stages!` in `phase.rs`, wrap the code it covers, and add it to
  `STAGES` (and, if older revisions run it, `LEGACY`) in the script. Stages must not hold
  one another.
- **A corpus:** add it to `corpus` and `CORPORA` in the workload. Keep it to a fraction of
  a second (callgrind runs it some fifty times slower), and never change an existing one's
  seed or size without saying so, as that resets its history.
